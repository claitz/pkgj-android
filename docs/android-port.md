# Android port

## Project

This repository contains the Android adaptation only. The Kotlin app lives under `android/`; Gradle wrapper, app sources, unit tests, and BSD license asset are self-contained there. The application ID is `org.pkgj.android.catalog`.

The app has Catalog, Downloads, and Settings tabs across the top. Settings includes an About section with the build version, original PKGj project, Vita3K compatibility source, and bundled BSD license. The library shows PS Vita content only and opens on Games. Category, region, compatibility and sort choices use compact menus. Region and compatibility menus accept multiple selections; selections within each filter are combined with OR, and filters are combined with AND. An empty selection means any region/status. PSP, PS1 and PS Mobile are excluded from browsing, settings and automatic catalog updates. Their legacy category identifiers remain readable so an upgrade does not break existing download records. Compatibility filters apply to Games; selecting another category clears the status filter. Compose renders paged SQLite catalog results. Paging queries run on the IO dispatcher and preserve coroutine cancellation, keeping filter changes off the UI thread. Landscape uses a shared search/filter toolbar, 48 dp catalog rows, compact download rows with actions beside the title, and two Settings columns with About links underneath. The header identifies the app as PKGj Android. A repository coordinates preferences, catalog refresh/import, downloads, and compatibility reports. WorkManager runs persistent foreground download jobs. New downloads write directly into a folder granted through Android's Storage Access Framework. Each job persists its folder and PKG/RIF document URIs. The shared HTTP transport writes to a seekable destination backed by a document file descriptor, checks destination space when available, and keeps partial files in that folder. It renames the PKG after transport completion and saves the matching RIF there. No private package or RIF copy is created for new jobs. Existing private downloads remain accessible and can be moved with Save to folder; successful moves remove the private copies. No all-files permission is requested.

The TSV parser follows the upstream PKGj column layouts, handles BOM and line endings, skips malformed rows, and stores catalog rows in SQLite. Vita game/demo entries can include an upstream zRIF. When present, the app converts it to a `.rif` alongside a completed PKG; it does not fabricate missing license data. New filenames use `[REGION-TITLEID] - Title vVersion` when those fields exist.

## Vita3K integration

The official [Vita3K Android manifest](https://github.com/Vita3K/Vita3K-Android/blob/android/android/src/main/AndroidManifest.xml) exports its launcher activity, but its `ACTION_VIEW` file filter is commented out and it declares no public PKG import intent. Vita3K's [Android activity](https://github.com/Vita3K/Vita3K-Android/blob/android/android/src/main/java/org/vita3k/emulator/Emulator.java) opens its own document picker. Its [Install .pkg menu](https://github.com/Vita3K/Vita3K-Android/blob/android/vita3k/gui/src/pkg_install_dialog.cpp) accepts PKG files and then asks the user to select a `.bin`/`.rif` license or enter zRIF. The app therefore exports files for the user to select inside Vita3K; it does not attempt an intent handoff, write to Vita3K's private storage, or report a game as installed.

Use Vita3K's **Install .pkg** action and select the exported PKG. If Vita3K asks for a license, select its matching exported RIF when available or provide license information you own. Vita3K displays the installation result. PSP, PS1, and other unsupported categories are not represented as playable.

The app reads `app_compat_db.xml` from the [official compatibility release](https://github.com/Vita3K/compatibility/releases/tag/compat_db) and status names from the repository's [public labels API](https://api.github.com/repos/Vita3K/compatibility/labels?per_page=100). On app startup it checks the release asset's ETag/Last-Modified values, downloads changed data, and caches title status, report issue, and update time in SQLite. Cached labels remain visible offline. Settings can trigger a manual check. The site warns that reports may not reflect recent emulator changes; the compatibility repository says reports are not intended for Android. Treat these as community reports, not device-specific guarantees.

## PS Vita game updates

### Discovery and parsing

`updates/GameUpdates.kt` ports the manifest signing contract from [PKGj patchinfo.cpp](https://github.com/blastrock/pkgj/blob/bf746865ff4aed40cfb5aa1810bd2d2460f025f0/src/patchinfo.cpp), with the upstream BSD notices retained in that file and the bundled LICENSE. JVM `Mac`/`SecretKeySpec` compute HMAC-SHA256 over the ASCII bytes of `np_` plus the exact regional Title ID, using upstream's 32-byte protocol constant. Lowercase hexadecimal is inserted into `https://gs-sec.ww.np.dl.playstation.net/pl/np/TITLEID/HMAC/TITLEID-ver.xml`. No NDK/JNI is used. Invalid IDs are rejected rather than redirected to a different region.

PKGj selects the last `package` in document order. Its first `hybrid_package` after that package replaces the download URL while version and required firmware come from the parent. The Android parser preserves document order and scopes the hybrid to its enclosing package. It uses the hybrid's size, never the incremental parent's size for a hybrid payload; absent size remains unknown. Multiple hybrids and orphan hybrids are rejected as ambiguous or malformed. Firmware is decoded from the decimal packed integer using the same hexadecimal major/minor formatting as upstream. It does not sort versions, select the largest package, or treat attributes in comments as elements.

A SAX parser handles XML structure and escaping. Both external general and parameter entities are disabled, an entity resolver refuses external resolution, and DOCTYPE declarations are rejected. Downloads of XML are limited to 1 MiB, redirects are bounded, HTTPS cannot redirect to HTTP, and TLS verification remains enabled. HTTP 404 and a valid empty `titlepatch` mean no update; other HTTP failures, empty/malformed XML, invalid selected-package attributes, unexpected roots/status values, and Title ID mismatches are errors. Errors do not overwrite a previous successful cache entry. This follows the separate Found/NoUpdate/Error states in [PatchInfoFetcher](https://github.com/blastrock/pkgj/blob/bf746865ff4aed40cfb5aa1810bd2d2460f025f0/src/patchinfofetcher.cpp), with stricter malformed-manifest handling.

The Sony manifest host uses a private CA and SHA-1-signed certificates, which Android's generic [certificate-strength policy](https://github.com/google/conscrypt/blob/master/common/src/main/java/org/conscrypt/ChainStrengthAnalyzer.java) rejects. With explicit approval for this legacy exception, `SonyUpdateTls` configures individual HTTPS connections only to **gs-sec.ww.np.dl.playstation.net**. It does not change system TLS defaults or catalog/download clients. It pins **SCEI DNAS Root 05**, validates the certificate path with JVM PKIX against that trust anchor, checks dates, server usage, signatures and RSA/EC key strength, and verifies the hostname. SHA-1 RSA signatures are allowed for this scoped private PKI; MD2/MD4/MD5 are rejected. DNS SANs take precedence; Sony's current certificate has none, so its wildcard CN is checked using Android's certificate DN parser. Wildcards match exactly one label. No trust-all manager, unconditional hostname acceptance, HTTP downgrade or global algorithm-policy change is used. Online revocation checking is disabled because this private CA has no public revocation service; CA rotation or expiry will require updating the pinned certificate.

The public CA bytes match [fetchpkg's published CA](https://github.com/ps5-payload-dev/fetchpkg/blob/10c9bb95f651d594ba254c104ac96d0bc836ed2d/dl.c#L30), independently fetched over verified GitHub HTTPS; they are not trusted simply because a server supplied them. Only the public certificate bytes were used, not that project's TLS settings. SHA-256: `51d5a7833f67f1d1c6212f75997e4b83dada0f7910ba4b5a3fa4e9b7b9bc827c`. Sony also lists this CA family in its [BRAVIA technical manual](https://pro.sony/s3/cms-static-content/file/25/1237492002825.pdf). No production private key or game credential is included. Local TLS tests use an unrelated test-only CA and server key in the instrumentation APK; these are never trusted by the production client.

Checks run when a game's details are opened or when a new game is downloaded, on the IO dispatcher. They never run for the whole catalog. SQLite `update_checks` stores found/no-update results and their check timestamp, keyed by exact Title ID. Results under 24 hours old can be reused; the refresh icon always requests metadata again. Details use a compact update row with version, size and required firmware when present, a refresh icon, and **Download update** for the patch alone. Loading, no-update and failure states remain distinct. The screen does not show a separate Check for update button or check timestamp. It never calls an available patch newer than the user's installation.

### Queue and migration

Database version 7 adds job type, Title ID, patch version, the result cache, and a unique partial index for update jobs. Existing jobs are retained as `CATALOG`, including their URLs, progress, states, license data and document URIs. An update's identity is `update:TITLEID:VERSION`; repeat requests reuse its existing job, with failed/paused/canceled jobs sent through the existing retry path. Different versions remain separate. Updates use `[REGION-TITLEID] - Title - Update vVERSION.pkg`, plus the existing collision suffix if another file already occupies that name.

Database version 8 adds the automatic-check state, error and original region to base jobs, retaining all existing records. Existing jobs do not opt into automatic updates retroactively. A new game job persists a pending check; the queue checks metadata before its transfer, queues any available patch into the game's persisted folder, then downloads the base before its patch. Patch insertion and marking the check done share a transaction, so process death cannot lose the pending check or create duplicate patch jobs. Discovery failure is saved separately and does not block the base download. Downloads shows the error and **Retry update**; retrying a failed base download also retries a failed discovery check. Automatic discovery leaves already saved, queued, paused or canceled patch jobs alone. Manual **Download update** retains the existing explicit retry behavior.

Updates use the same folder picker, WorkManager queue, HTTP transport, notifications, progress, resume validation, cancellation, retry, finalization and deletion as catalog downloads. They remain download records rather than catalog categories. Their persisted type bypasses every catalog-license lookup, license repair, RIF generation/export and RIF cleanup step. They can complete with no catalog zRIF and no RIF sidecar. The queue labels them as Update plus version. The new controls have the existing controller focus ring and A/B handling; triggers can scroll the details body.

### Verified Vita3K workflow and license handling

The official Android source was checked at [72cee295](https://github.com/Vita3K/Vita3K-Android/tree/72cee295b9a2cee2f708d0a047aee8841e55159f). Its [PKG installer](https://github.com/Vita3K/Vita3K-Android/blob/72cee295b9a2cee2f708d0a047aee8841e55159f/vita3k/packages/src/pkg.cpp#L218) recognizes application category `gp` as `PKG_TYPE_VITA_PATCH` and routes it into Vita3K's own patch storage. Its [import dialog](https://github.com/Vita3K/Vita3K-Android/blob/72cee295b9a2cee2f708d0a047aee8841e55159f/vita3k/gui/src/pkg_install_dialog.cpp#L76) uses the normal `.bin`/`.rif` or zRIF prompt before calling `install_pkg`; it also explicitly reports update versions on success. The patch path passes the supplied zRIF to decryption, rather than exposing a separate public license-free patch intent. PKGj's [downloader](https://github.com/blastrock/pkgj/blob/bf746865ff4aed40cfb5aa1810bd2d2460f025f0/src/downloader.cpp#L165) accepts a null RIF and dispatches Patch separately; its [download finalization](https://github.com/blastrock/pkgj/blob/bf746865ff4aed40cfb5aa1810bd2d2460f025f0/src/download.cpp#L1240) writes a license only when one is supplied. The Android app does not copy a base-game zRIF into the patch job or synthesize an unrelated license.

Install the base game in Vita3K, download the patch for that same regional Title ID, then use Vita3K's **Install .pkg** picker to select the saved update. Supply the corresponding game license through Vita3K's own prompt if required by that build. No automatic import, silent installation, private-directory access, installed-version detection or successful real patch installation is claimed. Other Vita3K builds may differ from the Android source inspected here.

## Download recovery and controls

Database version 6 adds destination URIs and a persisted transport-complete flag without deleting previous jobs. If saving or renaming fails after the HTTP transfer, retry completes that step without downloading the payload again. A job becomes Downloaded/Saved only after finalization. State transitions use conditional database updates so cancellation cannot be overwritten by a worker finishing concurrently. Cancellation removes the partial documents; Delete removes the saved files after confirmation. Changing the configured folder affects new jobs; existing jobs retain their original destination.

The app opens download documents in `rw` mode, which the [Android ContentResolver API](https://developer.android.com/reference/android/content/ContentResolver#openFileDescriptor(android.net.Uri,java.lang.String)) specifies as seekable. Providers that cannot supply a writable seekable file fail with a folder error. URI permissions are retained through the document picker, without broad storage access.

L1/R1 switch the top tabs from any section, including search and dialogs. D-pad and left stick move focus, A activates, and B dismisses dialogs or leaves search. Search intercepts Up/Down: Up returns to the top menu; Down moves to the category filter and then the visible list. Controls have visible focus borders. L2/R2 page through the current list or scrollable view; holding a trigger accelerates catalog paging. The right stick also pages. Menus and dialogs register their own scroll target so paging does not move content behind them. Details keep Close and Download visible while their body scrolls; delete confirmation starts on Keep. Catalog position and filters survive tab changes.

Analog controls use Android's [documented controller axes](https://developer.android.com/games/sdk/game-controller/controller-input), including both trigger axis aliases. Input repeats stop on release, tab/window changes, or activity pause; simultaneous analog and digital trigger reports are suppressed.

## Limitations

- Vita3K installation remains a user action, and license material is not available for every catalog entry.
- The app cannot query a verified public Vita3K installed-games API.
- Android may defer background work under device-specific battery restrictions. WorkManager restores interrupted jobs as queued and preserves the saved transfer phase. Direct downloads require a writable seekable document provider; local shared-storage folders are the intended destination.
- Catalog URLs may be customized. TLS certificate checks are not bypassed; HTTPS redirects cannot downgrade to HTTP.

From `android/`, run:

```sh
./gradlew test lint assembleDebug
```

The project uses Gradle 8.9, Android Gradle Plugin 8.7.3, Kotlin 2.0.21, JDK 17, and Android API 35. The original 18 JVM tests cover TSV parsing, filenames, compatibility XML and validators, multiple region/status filters, state transitions, seekable destinations, free-space failures, HTTP resume validation, and synthetic license decoding.

Validation on 19 October 2026 passed `test lint assembleDebug connectedDebugAndroidTest`: 29 JVM tests and 29 instrumented tests passed, lint reported 0 errors, 15 warnings and 1 informational finding, and the debug APK was built. ## Physical-device checklist

For updates: open details for a real regional game ID, repeat with another region, refresh manually, reopen offline to inspect the cached result, and test a no-update/error response. Download a new game and confirm its available patch is queued automatically into the same folder, base first. Check discovery failure and Retry update without repeating the base transfer. Download a legally obtained patch, check that only the separate Update PKG is saved, and exercise backgrounding, pause/resume, cancellation, retry and reopening. Install the base first and import its patch from within Vita3K using the appropriate game license if prompted. Verify the result in Vita3K; the app does not detect installed versions.

1. On an AYN Odin or Android phone, open the library online and confirm catalogs and compatibility labels load. Check search, multi-select filters, D-pad/left-stick focus, A activation, B/back, and dialog focus in portrait and landscape. Switch tabs with L1/R1 from search and dialogs. Page with L2/R2 and the right stick, checking hold acceleration and immediate release. Check that paging inside a dialog or menu leaves the catalog behind it in place.
2. Queue a small test download, background the app, turn the screen off, and check its notification, progress, pause/resume, cancellation, and retry.
3. Stop the app during a download, reopen it, and verify the job does not appear completed prematurely.
4. Select a download folder and confirm PKG/RIF files appear there with no duplicate in app storage. Check that partial files disappear on cancellation, saved files can be deleted, failed finalization retries without another HTTP transfer, and an existing private download can be moved with Save to folder. Revoke folder access and check the error and recovery after reselecting that folder.
5. In Vita3K, install a legally obtained compatible PKG, select its matching RIF if available, and verify the result in Vita3K.
